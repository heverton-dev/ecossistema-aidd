A Tríade Canônica:
3 Fluxos de Criação & Entrega de Software

Uma arquitetura para dar total liberdade ao desenvolvedor. A partir de uma fundação canônica de regras (aidd-forge) e um intake interativo (aidd-planner), derive a mesma ideia de negócio em três caminhos industriais — hoje sem handoff automático entre as etapas, um achado real da validação de 18/09/2026.

1. A Fundação e o Cérebro de Planejamento

Nenhum código é escrito sem governança blindada e alinhamento prévio de requisitos.

🛠️
Autoridade Máxima

aidd-forge (O Ditador de Regras)

Dita e injeta todas as regras do projeto antes de qualquer funcionalidade:

  • ✓ Regras de Arquitetura Limpa e Fatias Verticais (VSA)
  • ✓ Governança de Economia Severa de Tokens
  • ✓ Quality Gates binários de pré-commit e pré-push
  • ✓ Isolamento de ambiente e proteção contra contaminação
🧠
Planning Engine

aidd-planner (Intake BDD/SDD)

Entrevista guiada com o usuário para mapear objetivos e restrições:

  • ✓ Coleta interativa da ideia, domínio e escopo de negócio
  • ✓ Gera o arquivo canônico PLANNER.json
  • ✓ Pergunta ao usuário: "Qual dos 3 fluxos você quer disparar?"
  • ⚠ Achado real: hoje sem handoff automático — aidd-generator recebe a ideia como texto livre, não lê o PLANNER.json

3. O Funil Universal de Convergência (Pós-Construção)

Não importa por qual dos 3 fluxos o software nasceu, a linha de chegada de produção é a mesma.

PASSO 1 CONVERGÊNCIA

aidd-master

Harmoniza o código em Monólito Modular: fatias verticais (VSA) autônomas para regras de domínio (src/modules/<slug>/ — nome real; "features/" nunca existiu) conectadas a um núcleo horizontal compartilhado (src/core/), com roteamento unificado. Gera também o frontend Next.js (frontend/, Lei #11).

PASSO 2 CONVERGÊNCIA

aidd-enterprise

Injeta blindagem de missão crítica: assina componentes por SHA-256 (inject) e detecta adulteração pós-injeção (verificar-drift). Bug grave corrigido 18/09: verificar-drift nunca havia sido implementado de verdade nesta ferramenta.

PASSO 3 CONVERGÊNCIA

aidd-ops

Cobre dois tipos de origem: stacks OSS por nicho (Fluxo 02) e monólitos customizados do aidd-master (Fluxo 01/03), motor auto-selecionado. Bug grave corrigido 18/09: deploy sempre implantava a mesma stack fixa, ignorando o que foi curado.

Quarteto Obrigatório (rotas reais, confirmadas no código):
/docs (Swagger) /docs/guia (Manual) /webhooks /mcp

* /swagger não existe no código — era um erro herdado de versões antigas da documentação.

4. Lei Inviolável #11 — Padrão-Ouro de Stack (adicionada 18/09/2026)

Todo fluxo que gera frontend passa a produzir Next.js 14 + TypeScript + Tailwind CSS por padrão.

Gerador único e compartilhado (componentes/compartilhado/src-core/nextjs_exporter.py) usado por aidd-master e aidd-factory. Os Studios nativos do backend (/docs, /webhooks, /mcp) não são reimplementados em React — o Nginx roteia por prefixo entre o backend Python e o novo serviço web (Next.js).

Pendência: aidd-bridge fica de fora — ele não gera frontend, importa o que já existe no projeto de origem (Lovable/v0/Bolt).
