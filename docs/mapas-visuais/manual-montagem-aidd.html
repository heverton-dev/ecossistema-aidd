Parte 0

Por onde eu começo

Toda aplicação começa com uma pergunta só: de onde você parte? A resposta escolhe o fluxo. O resto da montagem é igual para os três.

Só tenho a ideia pureFluxo 01 · /pure

O ecossistema escreve o sistema do zero, com teste antes de cada pedaço de código.

python ecossistema.py pure "Clinica Vet" saude encaixes ok

Passa pela etapa 3. As etapas 6 e 7 ainda são de fachada.

Quero aproveitar motores open-source prontos openFluxo 02 · /open ou /aidd-open

Escolhe motores abertos já existentes e cola as partes do seu negócio em volta deles.

python ecossistema.py open "Clinica Vet" saude quebra na etapa 3

No Antigravity use /aidd-open, porque lá /open abre arquivo.

Já tenho um app no Lovable, v0 ou Bolt freedomFluxo 03 · /freedom

Tira o app da plataforma, troca o banco por um PostgreSQL próprio e deixa tudo pronto para a sua VPS.

python ecossistema.py freedom ./export-lovable "Clinica Vet" saude quebra na etapa 3

O primeiro argumento é a pasta exportada da plataforma.

Dicas que valem para os três: acrescente --dry-run para simular sem gravar nada. Sem domínio informado, o padrão é saas. A entrega vai para projetos/<nome> dentro do ecossistema, ou para onde você mandar com --pasta.

O que todo app deve ter ao sair

Tela de API/api: o Swagger, com todas as rotas documentadas
Tela de webhooks/webhook: avisos automáticos para outros sistemas
Tela de MCP/mcp: o próprio app vira um telefone para agentes
Central de ajuda/docs: guia do usuário, atualizado a cada módulo novo
Stack padrão-ouroNext.js + TypeScript + Tailwind na frente; Python + SQLite WAL atrás
Pronto para subirDockerfile, docker-compose e testes de verdade

As quatro telas são a Lei #10 (Quarteto) e a stack é a Lei #11. Só muda se você pedir outra coisa explicitamente.

Parte 1

As peças da caixa

Estas são as suas anotações, peça por peça. O selo mostra onde você acertou e onde vale um ajuste.

quem pensa quem trabalha quem ensina e orienta quem vigia quem liga as partes

O cérebro

você acertou
LLM (Claude, GPT, Gemini…)

Muito inteligente, mas probabilístico: a mesma pergunta pode ter respostas diferentes. Ótimo para decidir e criar; ruim para repetir igual mil vezes.

Por isso a Lei #1 separa inteligência de força bruta.

O agente orquestrador

você acertou
a sessão do Claude Code, opencode, mimo…

O mestre de obras. Um cérebro com mãos: lê as regras, escolhe o manual certo, liga para fora, chama as máquinas e entrega o resultado.

Ele pode chamar ajudantes (subagentes), que são outras cópias dele com uma tarefa só.

A máquina

você acertou
script determinístico · 0 LLM

Faz o que é matemático e mecânico. Mesma entrada, sempre a mesma saída. Não pensa, não esquece, não inventa.

Ex.: scripts/catalogo_pecas.py gera o mesmo catálogo toda vez.

A ferramenta

você acertou
tools/aidd-forge, aidd-planner, aidd-ops…

Uma pequena fábrica com entrada, processamento e saída. Dentro dela trabalham máquinas e, às vezes, o cérebro. Deve ser especialista em uma tarefa só.

São 8 hoje. Chamadas sempre por python ecossistema.py <nome>.

O manual de tarefa

ajuste
skill · SKILL.md

Uma receita escrita que ensina o agente a fazer uma tarefa específica. O agente lê o manual e executa.

Ajuste: skill não é um agente. É o papel com as instruções. O mesmo agente pode ler 10 manuais diferentes ao longo do dia.

Ver o mapa das skills, e como construir uma nova →

O regulamento

ajuste
rules · AGENTS.md

As regras da casa que todo agente lê ao chegar: idioma, formato de resposta, o que é proibido.

Ajuste: regra é um pedido, não uma trava. O cérebro pode esquecer. Só vira obrigação quando um guarda ou um alarme confere. Regra sem guarda é conselho.

O telefone externo

você acertou
MCP

O agente liga para fora e recebe uma resposta: documentação atualizada, GitHub, Cloudflare, o grafo do código.

6 ligados em .mcp.json. Outros 3 existem dentro das ferramentas, mas ninguém instalou o aparelho.

O alarme

ajuste
hook

Dispara sozinho num momento certo: antes de usar uma ferramenta, depois de editar, no início da sessão, antes do commit. Pode barrar a operação.

Ajuste: o hook é o quando, o guarda é o o quê. Normalmente o alarme toca e chama um guarda para inspecionar.

O guarda

você acertou
gate · gates/G_*.py

Um inspetor sem coração. Recebe o que foi produzido, confere bit a bit e responde só sim ou não.

Ex.: G_SEGREDOS barra senha no código. 42 guardas estão ligados ao commit.

O encaixe

faltava
contrato · handoff-*.schema.json

O tamanho do pino do LEGO. Diz o formato exato que a saída de uma peça precisa ter para entrar na próxima.

8 contratos em componentes/compartilhado/specs/.

A receita

faltava
fluxo · pipeline

A lista de montagem: qual peça vem primeiro, qual guarda confere cada etapa, o que acontece se falhar.

A Tríade (pure, open, freedom) são 3 receitas quase iguais. Veja a Parte 6.

Parte 2

O resto da caixa

Estas peças não aparecem nas suas anotações, mas trabalham o tempo todo por trás das outras.

O painel de botões

ecossistema.py · comandos slash

A porta de entrada única. Cada botão do painel liga uma ferramenta ou uma receita. Os comandos slash (/pure, /plan…) são os mesmos botões, apertados de dentro do chat.

17 comandos slash. python ecossistema.py help mostra o painel inteiro.

Ver o mapa dos comandos: qual skill cada botão chama →

Os moldes

templates/

Formas de ferro prontas. A ferramenta só despeja os dados do seu negócio dentro delas, sem inventar a estrutura do zero. É isso que faz dois apps diferentes saírem com a mesma qualidade.

Ex.: tools/aidd-master/templates/core, tools/aidd-factory/templates/vsa.

Ver o mapa dos moldes de entrega: o que cada ferramenta entrega →

O almoxarifado e o entregador

componentes/compartilhado · components sync

Cada skill, hook e comando é guardado uma vez só, no almoxarifado. O entregador copia tudo para cada mestre de obras (Claude, opencode, mimo, Antigravity…), cada um na pasta que ele sabe ler.

Nunca edite as cópias em .claude/ ou .agents/. Edite o almoxarifado e rode components sync --tipo todos.

Ver o mapa dos harnesses: para onde cada peça é copiada →

O diário de bordo

secoes/ · handoffs · memória

O cérebro esquece tudo quando a sessão fecha. O diário guarda o que aconteceu: quais sessões rodaram, o que cada peça entregou para a próxima, o que foi decidido.

Ex.: secoes/INDICE-SESSOES.md, HANDOFF_PLANNER_ENGINE.json, ORQUESTRACAO_EXECUCAO.json.

Os fornecedores de fora

dependências externas

Skills e telefones feitos por outras pessoas, que o ecossistema usa. Ficam anotados numa lista, e uma máquina confere se todos estão instalados antes de começar.

39 declaradas em gates/dependencias_externas.json. Conferência: dependencia verify.

Ver o mapa das conexões: MCPs e hooks →

O produto entregue

o app gerado

A caixa que chega ao cliente. Não é peça do ecossistema: é o que ele fabrica. Tem padrão fixo, com as quatro telas, a stack padrão-ouro e a pasta pronta para subir no servidor.

Parte 3

Por dentro de uma ferramenta

Seu desenho de entrada → processamento → saída está certo. Aqui ele aparece organizado, com dois detalhes a mais.

Entrada

  • vem de uma pessoa ou de outra peça
  • num formato combinado (.md, .json, .txt)
  • pode ser a saída de outra ferramenta (o handoff)
  • tem configurações (flags, perfis)

Processamento

  • máquinas (scripts) fazem o repetitivo
  • o cérebro (LLM) entra só onde precisa pensar
  • lê manuais (skills) e segue regras
  • pode ligar para fora (MCPs)
  • tem alarmes instalados (hooks)
  • roda numa redoma: a worktree temporária, uma cópia isolada do projeto

Saída

  • formato combinado (.md, .json, .yaml, .pdf)
  • obedece a um contrato de encaixe
  • vai direto para o guarda
  • vira entrada da próxima peça

Detalhe 1. Você escreveu "determinístico | probabilístico" no processamento. As duas coisas convivem: o esqueleto da ferramenta (ordem, etapas, conferências) é sempre máquina; o cérebro só preenche as partes criativas.

Detalhe 2. Você escreveu "utilizar outras ferramentas (skills)". Uma ferramenta pode ler manuais à vontade. Já para usar outra ferramenta, ela deve chamar pela porta da frente (a linha de comando), nunca mexer por dentro. Hoje a receita da Tríade mexe por dentro do master e do planner, e isso deixa as peças grudadas.

Parte 4

O encaixe

Duas peças só se encaixam se o pino de uma tiver o tamanho do furo da outra. No ecossistema, o pino é o contrato: um arquivo que descreve campo por campo o que precisa ser passado adiante.

Encaixa exit 0

planner handoff-planner-to-engine generator

O planner entrega o plano no formato que o generator espera, e a chamada usa só opções que o generator aceita.

Não encaixa exit 2

receita factory curate --dominio factory

A receita do Fluxo 02 (open) pede --dominio, mas o factory só aceita --plano e --pasta. O pino tem o tamanho errado, e a montagem para aí.

Parte 5

O guarda

Entrada

A saída da ferramenta, exatamente como ela foi produzida.

Processamento

Conferência bit a bit, 100% máquina. Nada de "acho que está bom".

Saída

exit 0 · passaexit 1 · para tudo

O guarda não conserta nada. Ele só diz sim ou não. Quem conserta é a ferramenta, na próxima tentativa.

Ver o mapa completo dos guardas, e como construir um novo → Ver o mapa das leis: cada lei e o guarda que a prova →

Regra de ouro 1: quem fabrica não fiscaliza

O guarda fica fora da ferramenta. Hoje cada ferramenta carrega o próprio guarda de segredos, e as 4 versões já estão diferentes entre si.

Regra de ouro 2: guarda que nunca diz "não" é de mentira

Todo guarda precisa provar que reprova quando algo está errado (Lei #13). A etapa 7 da Tríade é um guarda de mentira: escreve "100% conforme" sem conferir nada.

A Tríade é a fábrica: ela produz apps. A oficina é outra família de receitas, que conserta e melhora a própria fábrica. É nela que vivem os planos, as auditorias e os ciclos.

Ver o mapa da oficina: todos os planos e ciclos →

Regra da oficina: aprovar um plano aprova o papel, não manda executar. Começar a obra é uma ordem separada.

O ciclo de auditoria (4F)

Para inspecionar uma ferramenta a fundo, a oficina roda quatro fases em sequência, cada uma numa redoma:

1 · Inspetorprocura os defeitos e escreve o relatório técnico
2 · Arquitetotransforma os defeitos em plano de evolução, ticket por ticket
3 · Construtorexecuta os tickets com teste antes do código
4 · Retornoo inspetor volta com a mesma lista e confere se melhorou
Ver o mapa da lente 15D: as 15 perguntas e como cada ferramenta se saiu →

Nada é juntado ao projeto principal sozinho: depois da fase 4, a obra para e espera a sua aprovação. O mapa de peças que gerou este manual é a fase 1 do ciclo mapa-pecas/ciclo-01.

Parte 9

Os mapas

Cada tipo de peça tem um mapa: a lista completa do que existe hoje e o jeito de construir uma nova. Os mapas não são escritos à mão. Um molde guarda o texto fixo, e o gerador preenche as listas e os números a partir do catálogo de peças.
