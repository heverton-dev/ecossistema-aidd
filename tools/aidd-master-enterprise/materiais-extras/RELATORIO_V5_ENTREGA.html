Contexto

O que foi pedido e como foi entregue

Execução

As quatro ondas

Nesta ordem — cada uma sobre a base validada da anterior.

01

Persistência Poliglota & Outbox Transacional

92407d3

O quê

Um DatabaseAdapter (Bridge) faz SQLite e PostgreSQL responderem à mesma API: um PostgresConnectionProxy traduz ? → %s, injeta RETURNING id para emular cursor.lastrowid, e converte o DDL AUTOINCREMENT → SERIAL. O Transactional Outbox Pattern grava cada evento de domínio na mesma transação da mutação, garantindo entrega at-least-once mesmo se o processo cair antes do EventBus.emit().

Arquivos

templates/v2/database.py · templates/v2/outbox_worker.py (novo) · scripts/add_module.py · scripts/compose_suite.py · scripts/aidd.py (--db)

18 testes · SQLite real ponta a ponta · suite gerada 7/7 gates
02

EventBus Distribuído & Jobs Resilientes

ff6600a

O quê

O EventBus virou fachada sobre um EventBusDriver plugável — InMemoryEventBusDriver por padrão, RedisStreamsDriver (XADD/XREADGROUP com Consumer Groups) quando EVENTBUS_URL é definido. O JobQueue ganhou persistência opcional em _jobs, backoff exponencial (2ⁿ×5s) e Dead Letter Queue após esgotar as tentativas, com painel GET /api/jobs e POST /api/jobs/reprocessar.

Arquivos

templates/v2/events.py · templates/v2/jobs.py · scripts/compose_suite.py

29 testes · servidor real: outbox pendente→processado em 0,4s
03

Frontend Híbrido & SSO Corporativo

58efc13

O quê

aidd.py export-frontend --stack nextjs introspecciona o RouteRegistry gerado e escreve um Next.js 14 (App Router) + TypeScript + Tailwind completo, com types.ts inferido dos exemplos OpenAPI. O OIDCService implementa Authorization Code + PKCE (RFC 7636) com validação RS256 do id_token via JWKS, expondo /api/auth/oauth/login e /callback — o login local por JWT continua ativo sem nenhuma dependência extra quando o SSO não está configurado.

Arquivos

Verificação Real

Bugs encontrados e corrigidos

Nenhum destes apareceria em uma auditoria puramente estática — todos vieram de rodar um servidor de verdade e bater nas rotas com curl.

OndaOrigemO que quebravaCorreção
1 Introduzido PostgresCursorProxy não capturava lastrowid quando a query já tinha RETURNING Separada a emulação de RETURNING da captura do lastrowid
2 Introduzido Gate G_SEGURANCA reprovava um UPDATE com SET montado via f-string (falso-positivo de SQL injection) Reescrito como métodos de transição com SQL 100% estático
2 Pré-existente v4 Rotas de módulo nunca chegavam ao servidor HTTP — cada routes.py tinha seu próprio RouteRegistry isolado Corrigido com include_registry(); substituído no merge pelo fix upstream (Singleton)
3 Introduzido MCPServer(DB_PATH) quebrava com NameError em modo --db postgres DB_PATH definido também no modo Postgres (MCP segue SQLite por design próprio)
3 Introduzido OutboxWorker começava a sondar o banco antes do schema dos módulos existir — database is locked transitório Workers de background movidos para depois da inicialização de schema
4 Introduzido Um % literal em texto de ajuda do argparse ("100% dos cenários") derrubava todo comando da CLI Escapado para %%

Reconciliação

O encontro com o main remoto

No momento do push, o origin/main já tinha avançado 6 commits — alguém havia corrigido, em paralelo e de forma independente, o mesmo bug de roteamento da Onda 2, mas transformando RouteRegistry em um Singleton (toda instância no processo passa a compartilhar o mesmo estado), além de rotas de favicon, arquivos estáticos e um CSS 100% offline.

O conflito textual

Um único ponto de conflito em scripts/compose_suite.py: meu bloco de /metrics e os blocos de /favicon.ico/estáticos do main tentavam ocupar a mesma posição em _handle_get(). Resolvido colocando os dois lado a lado — são independentes.

O conflito que o Git não via

Mais sério: minha chamada registry.include_registry(registry_<módulo>) (Onda 2) e a lógica equivalente em openapi_to_ts.py (Onda 3) passaram a mesclar o Singleton nele mesmo assim que o merge trouxe a mudança — o que entra em loop infinito dentro de RouteRegistry.mount(), que itera self.endpoints enquanto anexa a ele. Nenhuma marca de conflito indicava isso; só apareceu ao subir o servidor de verdade.

Como foi resolvido

As duas chamadas de mesclagem explícita foram removidas — o Singleton, sozinho, já resolve o compartilhamento de rotas de forma mais simples do que minha abordagem original. Servidor com 2 módulos testado depois do merge: inicialização sem travar, ambas as rotas respondendo, /favicon.ico, / e /metrics convivendo sem regressão.

Honestidade

Limites deste ambiente

‣

Docker Desktop não estava rodando. Os testes de integração real com Postgres e Redis (containers efêmeros) existem e rodam automaticamente se o daemon estiver disponível — aqui, pularam com motivo explícito. A lógica crítica (tradução de placeholders, emulação de lastrowid, tradução de DDL) foi validada com duplos de teste determinísticos no lugar disso.

‣

terraform e helm não estão instalados. Os arquivos gerados foram validados estruturalmente — um "fake render" substitui cada expressão {'{{ }}'} por um placeholder e faz o parse do YAML resultante — em vez de terraform validate/helm lint reais. Os testes com os binários reais existem e rodam sozinhos assim que instalados.

‣

pyjwt e redis não são adicionados automaticamente ao requirements.txt quando SSO ou EventBus distribuído são usados — diferente de psycopg2-binary (Onda 1) e behave (Onda 4), que ganharam esse tratamento. Hoje, o erro de import lazy já orienta o pip install correto; adicionar a persistência em requirements.txt fica como polimento pendente para uma v5.0.1.
